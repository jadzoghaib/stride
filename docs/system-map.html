STRIDE

The whole system on one canvas

Every part of Stride and how a request travels through them — top to bottom, browser to database. Five numbered zones, matching the walkthrough underneath.

The same thing in words

Five steps, matching the numbers on the canvas.

  1. 1

    In your browser

    One JavaScript app. Some pages anyone can open — the athlete and club directories, public profiles. The rest sit behind a sign-in, and what you see there depends on whether you're an athlete, a sponsor, a club or a fan.

    Every call to the server goes through one small piece of code. It attaches your session, turns error codes into readable sentences, and notices when your session has expired.

  2. 2

    At the edge

    A web server sits in front. It hands out the app's files, and anything starting with /api it passes back to the API. That's its entire job — it holds no logic and no data.

  3. 3

    The API — one process

    Before a request reaches any code that matters, it runs the same gauntlet every time: cross-origin rules, security headers, a rate cap, a size cap, the failure-injection layer, and finally the step that stamps it with an ID, logs it and counts it.

    Then it lands in one of six areas — sign-in, athletes, clubs, sponsors, discovery, admin. Two other things live here: the engine that scores campaign briefs against athletes, and the health endpoints a load balancer polls to decide whether this copy is fit to receive traffic.

  4. 4

    The analytics engine

    This is not a separate service. It's a library running inside the same process, and that's the most important thing on the canvas. It pulls data from Instagram, YouTube and TikTok — simulated for now, but through the real pipeline — stores it, computes the KPIs, then scores.

    Because the data is simulated but the path is real, switching to live platforms changes one class per platform and nothing downstream.

  5. 5

    The data

    One database holds both the product tables and the analytics tables. It's a file on disk by default; point it at a Postgres address and it uses that instead, with no other change.

    The dashed line matters: the API and the analytics engine share a single connection, so anything that touches both either saves together or fails together. Split them into separate services and you'd have to build that guarantee yourself.

How many moving parts is that, really?

  • Two programs run in a deployment — the web server and the API. That's it.
  • The analytics engine isn't one of them. It's a library inside the API, which is why it can share a database connection rather than a network call.
  • The database is a file until you point it at Postgres.
  • Everything else on the canvas — routers, the matching engine, connectors, scoring — is a module inside one of those two programs.
