STRIDE

How it works, one question at a time

Seven small flowcharts covering the whole system — four for what happens in the browser, three for what happens on the server. Every card stands alone. Nothing here needs you to remember the card before it.

How to read these

One rule, used in all seven: down means you carry on, sideways means you stop there.

01

In the browser

The life of a session, in order: you arrive, you move around, a screen loads, your session expires.

Browser · 01

You open the app. What happens?

Short versionThe app asks the server who you are, then sends you to your own home screen.

Browser · 02

You click a link. Who decides what you're allowed to see?

Short versionThree questions in a row. Fail any one and you get sent somewhere else instead.

Browser · 03

A screen is loading. What are you actually looking at?

Short versionOne of four things — and never a blank page. Every screen has a designed answer for “nothing to show”.

Browser · 04

Your session expires while you're using it. Then what?

Short versionOne piece of code watches every request. The moment the server says “that session is dead”, it takes you to sign-in.

Browser · 05

Four kinds of people. Where does each one land?

Short versionYour role decides your home screen and your menu. One list in the code answers both.

RoleLands onMenu
AthleteTheir dashboardDashboard · Deals · Profile · Directory · Clubs
SponsorTheir campaignsCampaigns · Pipeline · Directory · Clubs
ClubClub HQClub HQ · Directory · Clubs
FanDiscoverDiscover · Following · Clubs
AdminThe athlete directoryDirectory · Clubs · Operations

This is a table rather than a flowchart because there's no decision to follow — it's a lookup. Every redirect in the app asks this same list, so there's only ever one answer to “where does this person belong?”

02

On the server

Follow one request all the way down: where it goes, what happens to it, and where it finally lands.

Server · 06

Where does a request actually go?

Short versionBrowser → the web server → the API → the database. The analytics engine isn't a separate service; it's a library sharing the same database connection.

Server · 07

What happens to a request on the way through?

Short versionIt gets a tracking ID, its role is checked, the work runs — and a log line and a counter fall out the bottom.

Server · 08

Two different databases, one set of code. How?

Short versionOne setting decides. Everything above that fork is byte-for-byte identical — a small translator absorbs the difference.

Three things these charts don't paper over

  • Admins have a menu item that goes nowhere. The admin menu links to an Operations screen that was never built. The server side of it exists and works — the screen just isn't there, so admins clicking it land on a “page not found”.
  • Two screens skip the loading state. The athlete directory and Discover flash empty for a moment instead of showing a skeleton. Twelve of the fourteen data screens do this properly.
  • The big board header is on one screen only. The redesign's signature element carries the athlete dashboard. Everywhere else got the colours and type without the layout.
